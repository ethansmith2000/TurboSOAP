**Disposition: minor revision for reproducibility and provenance wording.** I found no material numerical discrepancy in the abstract or five tables. **Findings requiring correction or clarification**

**1. Medium — the advertised exact recipe omits execution settings that define its precision behavior.** This is a reproducibility omission, not evidence that the reported results are wrong.

Location: DRAFT §§3.1, 3.3, and 4, particularly lines 84–98, 180–188, 240–245; `REPRODUCIBILITY.md` “Optimizer entry point” and “Exact recorded recipe,” lines 35–93; `configuration.json` → `recorded_runtime` / `optimization`.

The main worker explicitly selects `torch.set_float32_matmul_precision('high')`, deterministic algorithms, and `allow_bf16_reduced_precision_reduction=False`. The frozen seed-205 source records these at `/workspace/optimizer_replay_results/soap_bf16_full_20261026_seed205_v1/source/benchmarks/bf16_storage_screen.py:179–182`; the seed-204 worker uses the same storage-screen source hash. Its archived service wrapper also sets `CUBLAS_WORKSPACE_CONFIG=:4096:8` and thread/compiler/cache settings. These choices are discoverable through the pointers, but absent from the compact “exact” recipe and example. In contrast, §5.4 explicitly names the synthetic profile's `high` mode.

This matters because FP32 tensor dtype does not specify full-mantissa matrix multiplication. The installed primary API documentation at `/venv/main/lib/python3.12/site-packages/torch/__init__.py:1609–1666` distinguishes `high` from `highest` and states that internal precision can change without changing output dtype. The main QR products in `bf16_soap.py:58–64` cast operands to FP32 but inherit this setting. Similarly, the harness's disabled BF16 reduced-precision reduction is relevant to the manuscript's FP32-accumulation policy. I have not inferred which internal GEMM algorithm ran.

Recommended textual correction: add, “Both main arms used FP32 matmul mode `high`, deterministic algorithms, and disabled BF16 reduced-precision reductions; FP32 tensor/solver dtype does not imply `highest` GEMM precision.” Add the recorded `CUBLAS_WORKSPACE_CONFIG`, thread settings, and cache policy to the reproduction recipe, explicitly distinguishing the historical harness configuration from the standalone optimizer constructor. All values already exist in frozen sources and `service/*.sh`.

**2. Low — the blanket statement that source hashes are identical across seeds is too broad.**

Location: DRAFT §1, lines 44–45: “The policy, precision rules, and source hashes remain fixed across the two main candidate runs.”

The production optimizer pins and shared `bf16_storage_screen.py` pin do match. However, the two campaign manifests assign different hashes to `benchmarks/bf16_full_horizon.py`: seed 205 has `6e0b5d4ca62b738b3d6a53f5658630bafa42ee942399a61b0968c3a6c3b8a2fb`, while seed 204 has `ef3f1909de68902b4b75e05063b00d232e7eb3ce7d9f3e9d18f01076c86b1d77`. See `reports/bf16_full_horizon_20261026_seed205/manifest.json` and `reports/bf16_replicate_20261027_seed204/manifest.json`, `source_files`. Comparing the frozen files shows seed parameterization and audit generalization, not a changed production optimizer.

Recommended textual correction: “The policy, precision rules, production optimizer hashes, and shared training-worker hash remain fixed; campaign-specific runners are separately pinned.” This preserves the substantive reproducibility claim without implying byte identity of every harness file.

**3. Low — the reproduction guide names nonexistent records for the original reference bundle.**

Location: `REPRODUCIBILITY.md`, “Main evidence and frozen execution records,” lines 120–130; DRAFT Appendix B delegates archive navigation to this guide.

The guide describes the listed bundles collectively as having `manifest.json` and `progress.json`. `/workspace/optimizer_replay_results/soap_owt_restart_20261026_v4/` instead contains `provenance.json` and `learn_status.json`; it has neither of those two filenames. Its launch wrappers/configuration are top-level `learning_launcher.sh` / `learning_supervisor.conf`, rather than in `service/`. The latter difference is partly accommodated by “where recorded” later in the guide, but the manifest sentence is unqualified. This is a navigation error, not missing provenance: I verified all 572 source pins in the original `provenance.json`, and its selected input and row-ID hashes.

Recommended textual correction: distinguish the original reference's `provenance.json` / `learn_status.json` / top-level launcher files from the later bundles' `manifest.json` / `progress.json` / `service/` records. The repository copy `reports/owt_restart_20261026/provenance.json` is already indexed by `evidence.json`.

**4. Low — describe the CPU checker as checking repeated-prefix endpoint agreement, rather than complete prefix identity.**

Location: `REPRODUCIBILITY.md`, “Paper artifacts: CPU only,” lines 11–14; corresponding claim-map introduction and DRAFT Appendix B's reconstruction claim.

`paper/build_artifacts.py:77–100` checks equality at call 2000 among the cached warm control, main candidate, and development pilot. It does not compare every shared validation observation or a complete prefix's model/optimizer tensors. The same checker reads saved timing means at lines 70–83; it does not independently aggregate raw event timings. Its four production-source checks are also narrower than checking every frozen harness source. These are reasonable checks for a paper builder, but “repeated-prefix identity” can suggest stronger verification than it performs.

Recommended textual correction: “The checker verifies shared initialization identities and repeated-prefix endpoint CE agreement, reconstructs tables from saved scalar summaries, and checks the listed hashes. Frozen campaign audits provide the broader execution checks.” Keep scalar reconstruction distinct from rerunning or independently auditing training.

This is not a detected prefix discrepancy: I independently compared all eight common validation observations at calls 0, 50, 100, 200, 500, 1000, 1500, and 2000 between `reports/bf16_learning_20261026/comparison.json` → `results[3]` and the seed-204 main candidate, and they match exactly. The original full reference also equals the cached quality reference after the documented addition of `initial_gradient_sha256`.

**Verified results and interpretation**

- **Endpoint quality, §5.1 and abstract:** raw validation events agree with the result arrays. Seed 204 gives CE 3.4111515320837498 versus 3.422388957813382, delta 0.011237425729632378; seed 205 gives 3.4092715363949537 versus 3.4193537402898073, delta 0.010082203894853592. Computing `100*expm1(delta)` gives 1.130080277% and 1.013320055%. The mean paired delta is 0.010659814812242985. The abstract and table round these correctly. Sources: the two main `comparison.json` files and their `runs/*/events.jsonl`.
- **Timing, §5.2 and abstract:** recomputing raw update-event means reproduces 380.740033883/314.637875878 ms for seed 204 calls 101–200, and 380.548487439/309.532919492 ms for seed 205 calls 101–10000. Reductions are 17.361493965% and 18.661371755%. Seed 205 includes 990 stock QR events versus 198 candidate QR and 792 warm events in that window, with 8,910 ordinary events per arm. These are 198 full 50-call cycles; seed 204's paired window contains two. The cached seed-204 full reference is correctly used for quality rather than relabeled as fresh full-horizon timing. Its replay validation exactly matches calls 0/50/100/200. Sources: main `runs/{qr10,bf16}/events.jsonl`, replication `paired_prefix_timing`, and `benchmarks/bf16_hybrid_confirm.py:41–50,93–107`.
- **Timing scope:** the worker sums synchronized forward/backward and optimizer wall intervals, excluding the intervening physical-M observation, evaluation, logging, and LR-assignment work. The optimizer interval includes packing/writes and auxiliary AdamW through `SplitOptimizer.step`. The draft's exclusions and warning against interpreting these means as first-use compilation or whole-run time-to-quality are appropriate. Sequential pairing does not create independent device/campaign replications; the present language does not claim that it does.
- **Memory, §§3.4/5.2 and abstract:** the four declared groups imply 622,854,144 elements across the six state tensors. FP32 contributes 2,491,416,576 bytes; BF16 contributes 1,245,708,288 bytes, with 32 additional bytes for the four groups' FP32 age/LR scalars. The reported BF16 total, 1,245,708,320, is therefore correct. “Approximately 50%” handles this distinction. Saved seed-205 peaks are 10,090,324,992 and 8,829,772,800 allocated bytes, or 9.397347450 and 8.223366737 GiB: approximately 12.49% lower peak allocation. The manuscript correctly distinguishes that observation, including diagnostics, from persistent state and device reservation. Sources: `bf16_soap.py:219–237`, worker state-byte/peak accounting, and seed-205 `comparison.json`.
- **Controls, §5.3:** all three endpoint values, both CE differences, and all timing means agree with saved evidence. QR20 beats warm at six of seven noninitial evaluations; warm beats QR50 at all seven. The cached warm timing is correctly qualified as coming from another launch. Calls 101–2000 form 1,900 calls and complete cycles common to both cadences. These observations support the stated early-prefix comparison, not a final-horizon ranking or an additional seed.
- **QR profile, §5.4:** all table medians recompute from the ten stored CUDA-event samples. The displayed 0.95–4.63% reductions and disagreement counts agree with `reports/bf16_qr_attribution_20261027/result.json`. Maximum physical-M/next-update relative differences are 0.0009063121/0.0011160002, and minimum cosine is 0.999999404, consistent with the text. The synthetic inputs, batch size, FP32-output scope, nonadditive component medians, and one-factor BF16 probe are appropriately disclosed. This evidence cannot be used to subtract a hypothetical optimized-baseline speed from the training comparison; the manuscript does not do so.
- **Provenance and figures:** all 12 indexed evidence-input hashes, all four production optimizer pins, and both copied/source figure hashes match the snapshot inventory. The five table blocks and both generated JSON records match the builder's calculated outputs. Compact main/control/profile records match their original bundle copies. Every source-file pin in the inspected original-reference, two main, control, and profile bundles matches its frozen source. Figure-generation code uses the reported validation observations and medians; its treatment of call zero agrees with the captions. These checks establish local consistency, not independent authentication of historical execution.

**Presentation improvements; not factual errors**

The title accurately describes the implemented method and does not promise universal superiority. The abstract identifies the original stock-beta QR10 comparator, reports an explicit endpoint penalty, and separates its two timing windows. I would optionally add “Endpoint gaps follow larger observed early gaps of 0.118–0.124 CE at call 500,” drawing directly from §5.1, so readers see the trajectory cost alongside endpoint efficiency. The existing body already discloses it; this is not grounds for declaring the abstract numerically false.

Make the tables self-contained with short captions: “Full validation at call 10,000” for §5.1; “synchronized steady-step wall means, excluding evaluation/diagnostics/startup” for §5.2; and “seed 204; 10k LR horizon; timing calls 101–2000; warm timing from a separate launch” for §5.3 and Appendix A where applicable. Label §5.4's numeric times explicitly as medians. These changes reduce misreading when tables are extracted from their explanatory paragraphs.

**Unresolved questions for the authors, answerable without new experiments**

- Which frozen worker sources, service wrappers, input/row-ID records, and raw event logs will accompany the eventual manuscript artifact? The current local paths work here, but an external reader needs access to the referenced bundles or an explicit narrower promise of scalar-only reproduction. The paper inventory presently hashes the replication manifest but does not directly index every campaign manifest.
- Is “FP32 reference” intended to denote state/tensor/solver dtype throughout? If so, state that once alongside the shared `high` GEMM setting, avoiding an implication of `highest` arithmetic.
- Will all source consistency statements be restricted to the production optimizer and shared worker, with campaign-runner differences separately documented?

The already acknowledged limits—two initialization seeds with fixed data order, a development validation panel, approximate M/V transport, finite diagnostic screen crossings, short sparse-QR controls, synthetic local attribution, and no checkpoints—should remain visible. They are not new factual errors or acceptance vetoes. An optimized FP32 QR10 run is not required to substantiate the current comparison against the original implementation. The existing evidence is sufficient for this scoped case study after the documentation corrections above.
