# BF16 storage and long compiled regions: opt-in candidate

This is a separate numerical/implementation candidate, `bf16_soap.CompiledSOAP`.
The completed FP32-state `FastSOAP` results and source remain unchanged.

## Precision contract

FP32 master parameters retain small updates. Persistent M, V, covariance factors
and bases can independently use BF16 (bases may instead remain FP32). Counters,
learning-rate scalars, normalization, moment pointwise arithmetic, eigen/QR
decompositions and BF16 GEMM accumulators use FP32. BF16 M/V are rounded after
each call; this call's direction uses unrounded updated moment temporaries.
Most projections, covariance products, rotations and transports use BF16 matrix
operands/results. Selected last products have FP32 outputs. FP32 bases retain
FP32 Gram calculations. This changes arithmetic even in the FP32-storage mode.

There is no global BF16 autocast around the optimizer. Dtype boundaries are
explicit; compilation may fuse pointwise casts without deleting BF16 rounding.
Whole same-shape batches include stacking parameters/gradients, SOAP updates,
covariance accumulation, optional refresh/transport, and master-parameter writes
inside `fullgraph=True` regions. Eigh initialization is eager; QR is a supported
external solver within the captured graph. Auxiliary AdamW and model forward/
backward remain the existing recipe. Four shape groups cover all 48 matrices,
including both factors of tall/wide matrices. Optimized QR reuses C@Q and a
column contraction for sorting. No ridge, padding, blocking or coverage change.

## Predeclared bounded screen

Bundle: `/workspace/optimizer_replay_results/soap_bf16_storage_20261026_v3`.
Four fresh subprocesses, sequentially on one lifetime GPU claim:

1. Existing FP32-state FastSOAP with its compiled warm refresh.
2. Fully compiled batching, FP32 persistent state, BF16 matrix operands.
3. Same compiled batching with BF16 M/V/C/Q.
4. Same compiled batching with BF16 M/V/C, FP32 Q.

Fixed seed 204, stock betas (.95/.95, covariance .95), warm10/QR50, matrix peak
LR .0015, auxiliary AdamW and 10k-call LR schedule unchanged. Same 109M model,
first 201 global batches of the frozen OWT restart input (32 x 1024), physical
batch 8. Validation uses the first 128 frozen validation rows at calls 0, 50,
100, 201. This shorter panel is explicitly not the completed study's full panel.

Report optimizer/complete-step timing for calls 101..200 (two full 50-call cycles),
including stacking and parameter writes. Diagnostics are outside timed regions.
Report compile/startup elapsed time, capture counters, persistent matrix-state
bytes and peak allocated GPU memory (including diagnostic work). Initial weights
and initial gradients must match across arms. No model/optimizer tensors are
saved. Each arm exits, releasing its compiler/CUDA context.

Before training, CUDA eager/compiled checks cover ordinary/warm/QR transitions
on small matrices. Gates: parameter max absolute difference <2e-5 and state
relative difference <2.5%. A same-state BF16/FP32 direction probe reports a 2%
relative / .999 cosine engineering screen; it is not learning equivalence.

At initialization and refresh ages 10, 50, 100, 150, 200, check finite state,
nonnegative V, Gram errors and actual physical-M round-trip error. Keep reporting
the original FP32 guard (absolute Gram <=.05 and normalized <=.005). Separately
report a **precision-specific** guard: normalized Gram <=.005 and physical M
error <=1%. Full BF16 Q can exceed the original absolute Gram limit simply from
rounding large orthogonal matrices; record the fresh BF16-rounded QR floor at
initialization rather than silently treating that limit as passed. Failed
accuracy guards mark the candidate unqualified; only nonfinite/invalid state
or resource/compile checks abort the bounded screen.

Limits: 30 minutes/arm, 24 GiB peak allocation, one GPU, no automatic restart.
The screen combines batching, compilation, efficient QR and changed arithmetic;
its speed relative to the original is an implementation comparison, not a
BF16-storage-only attribution. Compare compiled arms to isolate storage choices.
Early CE is a smoke test; multi-seed/full-horizon evidence remains necessary.

The preserved v1 attempt stopped after its first cold call because the screen
logger's event argument collided with the update-kind field. It produced no
completed arm or usable timing comparison. The v2 logger uses a distinct name.
The v2 original control completed; the compiled FP32 arm reached call 50, then
hit Dynamo's default eight-entry cache limit: compiling `functools.partial`
placed all event/shape variants in one shared wrapper. In v3 the three event
functions are compiled directly and arguments are bound afterward. A regression
test captures all 12 event/shape graphs and repeats them at changing LR without
raising that limit or falling back to eager execution. All arms restart fresh.

## Completed result

All four v3 arms completed on the same claimed RTX 5090. Initial parameter,
initial gradient and initial validation values match exactly. Source/input
hashes, 804 training calls (26,319,744 targets), 2,304 factor observations and
960 actual-M observations passed the completion audit. Evidence is in
[`reports/bf16_storage_20261026/`](reports/bf16_storage_20261026/).

Clean calls 101..200, two complete refresh/repair cycles per arm:

- Existing FastSOAP: optimizer **52.410 ms**, whole step **336.736 ms**;
  matrix state **2.320 GiB**, peak allocated **9.394 GiB**; call-201 CE **5.768373**.
- Compiled FP32 storage/BF16 arithmetic: **29.862 / 316.026 ms**;
  **2.320 / 9.380 GiB**; CE **5.777460**. Step time falls **6.15%**.
- Compiled BF16 M/V/C/Q: **26.108 / 310.666 ms**;
  **1.160 / 8.218 GiB**; CE **5.768391**. Matrix state halves, optimizer time
  falls **50.19%**, whole-step time falls **7.74%**, and peak allocation falls
  **12.52%** relative to the original implementation.
- Compiled BF16 M/V/C with FP32 Q: **28.425 / 314.579 ms**;
  **1.608 / 8.666 GiB**; CE **5.770981**. Matrix state falls **30.68%** and
  whole-step time falls **6.58%**.

Comparing the two fully compiled storage modes isolates a smaller incremental
benefit: full BF16 storage reduces optimizer time **12.57%** and step time
**1.70%** relative to compiled FP32 storage. Most improvement over the original
comes from the combined batching/compilation/arithmetic changes, rather than
storage alone. The FP32-storage compiled arm also uses BF16 projections and
transports, so its name describes storage, not mathematical equivalence to v1.

All three compiled arms captured **12 graphs**, unchanged from call 51 through
201, with **zero graph breaks**. CUDA eager/compiled parameter probes agreed
within the declared tolerance; same-state direction relative errors were below
2% and cosines above .999. Generated CUDA wrappers confirm direct BF16
`baddbmm` covariance EMA and BF16 projection/transport buffers. Full FP32
parameter-pack buffers and FP32 warm-generator/Gram temporaries still exist;
the implementation does not promise zero casts or a single fused GPU kernel.

The full BF16 basis fails the existing absolute Gram guard as expected
(maximum about **.13**), while passing the separately declared normalized
guard (maximum **.002363**). Actual physical-M error peaks at **.9924%**, just
under the 1% limit, at the first warm refresh. This is limited margin. FP32
bases reduce that peak to **.5045%** and pass both geometry guards. Compiled
FP32 storage peaks at **.4971%**; the original at **.1549%**. These are measured
transport errors, not guarantees on optimizer direction or convergence.

The four subprocess elapsed times were **99.1 / 153.8 / 144.0 / 133.1 seconds**
in the order above. They include evaluation, diagnostics and first compilation;
the new arms additionally include CUDA parity probes. Compiler disk cache was
shared sequentially within this fresh bundle. These elapsed times are not a
matched measurement of pure cold compilation, and short runs do not obtain the
steady-state timing benefit after accounting for startup. The source bundle's
compiler cache is outside the compact evidence directory.

This supports keeping both BF16 options available for experiments. It does not
replace the completed 10k-call FP32-state method as the paper's current evidence.
Next: a prospective longer matched learning run of full BF16 and the FP32-basis
alternative, then full-horizon paired replications if quality remains acceptable.
Keep the stock beta recipe and original comparator fixed. QR20/QR50 controls
and a symmetric efficient-QR attribution audit from the pre-freeze review remain
open; this implementation screen does not close those methodology questions.

Related-work attribution remains essential: Milligan et al.,
[Reparametrizing Shampoo and SOAP for Subspace Basis Updates and BFloat16 Storage](https://arxiv.org/abs/2605.26327),
already study BF16 storage for SOAP with a different representation. General
BF16 storage and compilation are existing techniques; any eventual contribution
must identify this dense kernel/precision policy and its demonstrated tradeoff.

## Usage

Use this matrix-only optimizer beside the existing auxiliary AdamW, outside
autocast. It groups equal-shaped FP32 matrix parameters internally.

```python
import torch
from bf16_soap import CompiledSOAP

matrix_optimizer = CompiledSOAP(
    matrix_groups,
    betas=(.95, .95), shampoo_beta=.95,
    state_dtype=torch.bfloat16,     # M, V, covariance
    basis_dtype=torch.bfloat16,     # torch.float32 for more numerical margin
    compute_dtype=torch.bfloat16,
    compile_kernels=True,
)
```

New candidate tests: **13 passed**, including reference agreement in FP32,
batched independence, dtype-preserving checkpoint replay, numerical rounding,
full-graph parameter writes, and the 12-specialization cache regression. An
earlier combined check also passed all **20** pinned-reference tests. No changes
were made to the original `soap.py`, `soap_reference.py` or `fast_soap.py`.
